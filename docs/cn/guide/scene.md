# 适用场景

fluth 适用于响应式编程场景，相比于响应式数据，用流的方式来组织代码具备以下优势：

- 更容易构建响应式的逻辑，降低业务复杂度
- 更加声明式的编程范式，能大量减少代码量
- 更加易于代码阅读，上下游关系一目了然

![image](/structure.drawio.svg)

## 构建响应式的逻辑

对于 vue 或者 react 的开发者来说，利用数据的响应式来触发视图的更新带来了开发效率的巨大提升，但是在逻辑层数据的响应式并没有发挥出应有的价值。

在业务逻辑中利用数据的响应式通常是利用 watch 来监听数据的变化（或者 useEffect 来监听数据的变化），然后通过数据的变化来触发逻辑的更新。但是这种方式存在以下问题：

- 语义差
- 数据流不清晰
- 时序问题难以管理

所以其使用场景比较有限，但是使用 fluth 的流式编程范式，可以将整个逻辑的构建在响应式中，从而实现开发效率的提升！

## 推荐场景

fluth 默认采用基于 `_rootPromise` 的覆盖式竞态语义（类似 `switchMap`，新值到来时会静默丢弃旧的未完成异步回调），非常契合「只关心最新结果」的前端场景：

- **查询类场景**：搜索框防抖请求、列表筛选条件切换拉取、Tab 切换加载数据。
- **渲染类场景**：异步派生状态计算、多数据源组合后驱动视图更新。
- **交互编排场景**：表单字段联动、级联下拉拉取、只关心最新输入结果的异步校验。

## 不适用场景

::: warning 注意
在**不能丢消息**的场景下，请勿直接依赖 fluth 默认的异步链式传播，详见[边界说明 - 竞态异步](/cn/guide/boundary#竞态异步)。
:::

- **WebSocket / SSE 连续推送消息**：连续消息进入异步 `then` 链路时，新消息会静默丢弃尚未完成的旧消息回调。
- **队列写操作与有序提交**：需要保证每一条写请求依次落盘或回调不丢失的场景。
- **高频埋点上报与日志收集**：在流节点直接返回上报 Promise 会导致未完成的上报链路被后续事件覆盖丢弃。

在这些场景中，建议在同步 `then` 中脱离流返回 Promise（独立触发异步副作用）、借助外部串行队列消费、结合 [`buffer`](/cn/api/operator/buffer) 批量处理，或选用更适合的队列 / RxJS 方案。
